# 4.2B-UI discovery (before implementation)

Inspected `feature/phase4-2-runpod-runtime`, the supplied v2 roadmap and Word specification (eight first-level mockups). Historical staging counts are not live measurements. No cloud inventory or production records were read.

* **Shell:** `dashboard/app.py` renders the login gate, Azure reservation, legacy live demo, then stops before development controls in production. `pages/` auto-discovers intake and worker drilldowns. Use explicit Streamlit navigation in cross-cloud mode; preserve the old workspace when that mode is off. `ui.py` has duration/time formatting, `auth_gate.py` validates login via `/me`.
* **Commands:** `azure_run.py` keeps the idempotency key across lost receipts and polls only the local record. `POST /api/v1/runs` returns `{run_id}`. `crosscloud/dispatch.py` reserves the remote ID and local binding atomically. The dispatcher alone resolves credentials and the pinned endpoint. The reviewed Azure adapter submits 100 tasks, concurrency 4; this UI submits a 120-second deadline. The adapter verifies 100 complete/zero failed before recording business success; interim remote task counts are not persisted.
* **Registry:** private `GET /api/v1/deployments` returns paged `items`, including operator references unsuitable for display. Fields include provider, runtime type, execution policy, capabilities, status, source and deployment ID; no friendly name, region, cost or live health. Registration is not reachability. Render a display allowlist.
* **History:** `RunQueryService.list_runs` mixes legacy demo rows and bindings; not exposed as an HTTP GET collection. `get_run_summary` returns an authorised binding plus optional dispatch state/attempts/error. Add a binding-only paged collection for this workspace; no schema migration or dispatcher changes.
* **Telemetry:** the legacy external browser queries `external_runs` (`items`), `external_summary` (object), `external_units/workers/timeline` (`items`) and unit detail (`spans`). These APIs scope by a source grant; omitting the source selects the first grant. They do not establish ownership of a local binding. Reuse the underlying OTLP projections and trace-table presentation, but resolve source + remote ID from an authorised local binding for workspace detail reads. Do not forward deployment configuration, raw attributes or credential references to tables.
* **Completeness:** `samples/azure-python-agent/app/benchmark.py` and `telemetry.py` in the sibling checkout support an explicit post-flush manifest to `/v1/traces/complete`. Code capability is not proof of emission by the deployed revision. `otlp_store.summary` requires the source manifest, matching span/unit counts and graph/conflict checks. Missing manifest means unverified completeness, even after successful ingest. `deployment_bindings.telemetry_status` is independently stored; uncertain-dispatch reconciliation inspects provider status, not traces. No reason to mutate either protocol or historical rows.
* **Isolation:** private app mount behind the cross-cloud flag, verified JWT + enabled allowlist + intersected scopes + owner/source grants. In staging the UI intentionally uses production login restrictions, no DB volume, and only the private API URL. Shared Docker image, isolated ingress, separate credential-bearing dispatcher. No need to change ingress, secrets or networking.
* **Regression surface:** dashboard login, Azure receipt recovery, external reads, receiver, cross-cloud registry/dispatch, production packaging and staging config. Add tests for history without spans, same remote ID across sources, denied reads, safe projections and shared selection. GPU/LLM allocation, collectors, cost and runtime control remain outside scope.
