# Phase 4.1-A: cross-repository contract audit

**Finding:** The saved Azure run is fully correlated *inside the producer*. AOB can store its graph and deduplicate it, but the external OTLP projection discards the evidence needed to report task outcomes and successful validations. An OTLP acknowledgement, business success, and AOB run completeness are three different results.

## Producer: identity, graph and delivery

- The **caller**, not the agent, supplies `external_run_id` (`azure-py-` + lowercase UUID-shaped text); the example generates a GUID. Strict request fixes task count at 100 and concurrency at four. Same-ID/same-body replay returns the in-process record without re-emitting; changed payload conflicts. Process history is bounded, not durable. See `AZ/README.md:45-54`, `AZ/app/models.py:6-22`, `AZ/app/main.py:17-18,49-55,76-115`.
- `Record.new` copies that value to `run.run_id`, assigns `INT-0001` through `INT-0100`, cycles `worker-01` through `worker-04`, and defaults each unit's `attempt` to 1. These are run-local logical workers, not machine or thread IDs. Four asyncio tasks each process every fourth unit (25 apiece). No independently generated `task_id`, `source_id`, or provider ID is emitted. `aob.unit.task` is a span name, not a task identifier. See `AZ/app/benchmark.py:21-33,48-55,77-85`, `AZ/app/models.py:18-22`, `AZ/app/telemetry.py:90-99`.
- Only inbound W3C `traceparent` is extracted into a fresh context. The SDK starts the run span using it (otherwise a new trace); each current-span scope and child asyncio task carries context. The local run span can therefore be a **child of a remote caller**. The API returns one 32-hex trace ID, not the run ID. No arbitrary baggage/tracestate or exception details are required. `AZ/app/main.py:102-110`, `AZ/app/benchmark.py:35-46,48-85`, `AZ/tests/test_runs.py:36-57`.
- Successful graph: `aob.azure.run` (1) -> `aob.azure.worker` (4) -> `aob.unit.task` (100) -> three **siblings** per unit: `agent.classify`, `tool.lookup`, `result.validation` (100 each). All carry run; worker and descendants carry worker; unit and descendants carry unit/attempt. Run has workflow, dataset version, seed and test mode; unit task sets business status, validation sets a boolean after the call returns. Successful spans need not set OTel `OK`; exceptions mark `ERROR`. An early failure can omit later steps. No model calls in this workflow. `AZ/app/benchmark.py:30-85`, `AZ/app/agent.py:5-36`; field-level evidence in the [matrix](phase4_1_alignment_matrix.md).
- `AOB_EXPORTER` defaults to console. OTLP uses the pinned HTTP exporter, `/v1/traces`, validated HTTPS or specified local exceptions, a separate bearer token and five-second exporter timeout. Always-on tracer, queue 2048, max batch 512, delay 5000 ms. The response hook requires HTTP 200 + protobuf MIME + decodable response with zero rejected spans; HTTP errors go to the SDK. An empty serialized default protobuf is a valid success. No dependency on AOB's count headers. `AZ/.env.example:1-8`, `AZ/requirements.in:4-6`, `AZ/app/telemetry.py:19-58,69-102`.
- `force_flush` alone is not success: the agent compares per-run deltas of successful batch span counts and failed batches to attempted emissions and records flush outcome separately from business outcome. Counts include acknowledged duplicates; console success only means console export. No completion POST in the run path, no durable spool (`AZ/app/benchmark.py:86-105`, `AZ/app/models.py:25-44`, `AZ/README.md:136-149`).

## Consumer: two contracts, not one

**External OTLP.** Public app mounts the OTLP router (`B/api/public_ingress.py:18-21`). `AOB_OTLP_SOURCE_TOKENS` is a server-side JSON source-to-token map. Receiver compares bearer credential to configured values and binds the matching source to every decoded row; never trusts a payload identity (`B/config.py:89-105`, `B/otlp_api.py:40-51,78-86`). This is not the agent's Run API token and not a private read credential.

`POST /v1/traces` requires exact protobuf request MIME (case folded), nonempty body, defaults of 2 MiB and 1000 spans. Malformed protobuf -> 400; missing/bad credentials -> 401; body/count limits -> 413; wrong MIME -> 415; no spans or invalid required content -> 422. Byte length checked after reading as well as against declared length; span count checked after decode. Resource/scope/span traversal checks nonzero 16-/8-byte trace/span IDs, nonempty string run ID, nonzero start and nondecreasing end. Unknown attributes are dropped; specific sensitive prefixes reject the request; recognized attributes retain only bounded scalars. Parent width/nonzero, name vocabulary and field-specific optional ID types are not enforced. Scope, most resource metadata, links/events are not persisted. Failure in decoding a span prevents insertion of the batch. After transaction, return protobuf success with accepted/duplicate headers (`B/otlp_api.py:15-37,51-120`; `B/otlp_store.py:33-68`).

**Storage and graph.** External rows have PK `(source_id,trace_id,span_id)`, source/run/time and source/run/unit indexes, nullable worker/unit/parent and JSON text for filtered span attributes. No task column or run-to-single-trace constraint. Same identity is first-write-wins even if a later run or payload differs. Parent lookup/late reconciliation joins on source + trace + parent span ID (not run); orphans are retained and annotated, not rejected. `POST /v1/traces/complete` is a separate authenticated JSON call: expected span/unit counts must match received distinct IDs/units, and every non-null parent must occur in that run and trace. It does not test acyclicity, identify legitimate remote parents, prove business success, or continuously refresh completion after later inserts. `B/otlp_store.py:10-25,33-68,91-112,137-150`, `B/otlp_api.py:123-140`.

**Cardinality verdict.** Multiple sources and multiple traces per source/run are representable; run rollups combine traces, raw timeline retains trace IDs. No provider dimension or first-class trace listing/filter in external read routes. A source is an authenticated namespace, not a cloud provider. Private routes pick the *first configured source*; storage capability does not imply usable multi-source browsing or authorization. `B/otlp_store.py:11-24,71-112,133-149`; `B/demo_api.py:286-322`.

**Kaggle compatibility boundary.** Signed `POST /api/traces` verifies run binding, signature, acceptance window and limits before ingest; it is not OTLP. `trace_batches` tracks `(run_id,batch_id)` and `final`; `trace_spans` keys `(run_id,trace_id,span_id)`, stores allowlisted resource JSON separately, accepts legacy hex widths and timestamp formats. LLM correlation walks ancestors within a trace for unit/worker/attempt; token coverage and unattributed calls are reported, not inferred from Azure classification. GPU counters come from typed run events, not these spans. See `B/demo_api.py:140-145,213-257`, `B/trace_store.py:11-39,82-116,123-155,170-225`, `B/security/event_schemas.py:191-209,213-239`, `B/workers/worker.py:95-100`.

**Decision for 4.1-B:** preserve both ingestion/auth paths and raw identities. Fix semantic retention and read-back before changing producers or claiming end-to-end acceptance. See the [schema proposal](phase4_1_schema_v1_proposal.md) and [implementation gates](phase4_1_implementation_plan.md).
